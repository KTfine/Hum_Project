# 纯文本模式切换测试：不修改提示词

日期：2026-11-07（Asia/Shanghai）。代码基线 684d582。仅测试模型能否根据文字输入生成模式切换标签，不修改 prompt.py、客户端或后端代码，不开启麦克风/摄像头，不发送录音、图片、视频或空白图片。

## 测试条件

- 使用现有 MiniCPM-o 4.5 服务的 chat WebSocket 接口。每次新建独立会话，发送 system + 单条 user，无历史对话污染；角色初始状态与普通客户端一致。
- system 内容通过现有 build_control_prompt 构建，指导/合照模板均原样使用，包含当前固定会话附加说明，没有为纯文本测试改写任何提示词。
- 32 种表达共 98 次调用：第一批 26 种各 3 次，补充 6 种各 3 次；“和我合照。”“恢复指导模式。”各有 1 次先行连接验证，一并计入，避免忽略先行失败。
- 每种表达至少重复 3 次，第二轮倒序运行。没有跨轮累积对话，也没有在用户输入中提醒输出标签。
- streaming=true，max_new_tokens=256，length_penalty=1.0，omni_mode=false，tts.enabled=false，use_tts_template=false，enable_thinking=false。chat 路径使用服务默认采样；不声称采用实时双工的 temperature/top_p/top_k 配置。
- 常规 18006 转发当时已断开；确认已有 SSH 动态转发连接的是同一指定服务器后，通过该通道访问同一网关。测试前后网关正常，结束后 1 个 worker 空闲、队列 0。未修改服务或终止其他连接。
- prompt.py 的 SHA-256 前后均为 fc730a01b4e2c273493beab7aa61e24affaeed22e640e36f266071433352c818。
- 检查全部 98 个真实发送载荷：system 文本与当前模板组装结果逐字相同，消息内容均为字符串，无音频/图像/视频输入，音频输出事件为 0。
- 原始输出使用项目 StreamingCommandParser 解析。仅口头说“已经切换”不算成功；带解释前缀但仍包含可解析正确 mode 标签，计为标签命中，单独说明其格式瑕疵。本轮不执行相机客户端的模式切换，不把生成标签通过等同于实时音视频端到端通过。

## 汇总

- 需切换的 21 种表达，65 次调用中 33 次生成预期标签。
- 不应切换的 11 种对照表达，共 33 次，均未产生错误模式转换；这只代表本轮对照，不代表不存在误触发。
- 较可靠的本轮表达：进入合照使用“切换到合照模式。”“进入合照互动。”“现在和我合照。”“我想和你合照。”，各 3/3；恢复指导使用“恢复指导模式。”4/4、“切换到真人拍照指导模式。”“切换到指导模式。”各 3/3。
- “我想和你合照。”其中一次输出含“切换到合照互动：”前缀及合法 mode 标签，因此切换可解析，但整段并非纯标签。
- “和我合照。”2/4、“请和我合照。”2/3；“我们合照吧。”“我们一起拍张照吧。”“退出合照。”均为 0/3。相近表达结果不同，不能推导成固定关键词规律。
- 典型失败：输入“和我合照。”只回复“好的，我们切换到合照模式。”；输入“退出合照。”只回复“好的，我们切换到真人拍照指导模式。”，均没有 mode 标签。
- 核心观察是“理解并口头承诺”经常没有转成可执行标签。说话协议也常见裸文字、说话前缀或错误的 speak 格式；本轮未把说话格式作为切换成功的替代判据，也未调整 prompt 修复它。
- 少量重复不证明长期稳定；纯文本 chat 的结果不等同于麦克风/视频双工效果。摄影建议是否正确、真人调整闭环及实际模式重建均不属于这次模型测试。
