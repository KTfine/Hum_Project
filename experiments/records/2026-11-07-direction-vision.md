# 人体左右、表情观察与视觉模块评估

日期：2026-11-07，Asia/Shanghai。状态：已执行；两版候选均未采用，正式 prompt 和运行代码未改。

## 结论

当前部署能在本轮简单合成照片中认出画面位置、正面和背面，但不能稳定把画面目标转换成人自身的左右。**不宜把持续摄影指导中的方向口令和到位确认完全交给当前 LLM 输出。** 这不等于证明 MiniCPM-o 4.5 在所有配置下都做不到，也不能把所有失败归因于视觉编码器。

| 检查 | 实际结果 | 可以支持的结论 |
|---|---|---|
| 画面左 / 中 / 右及正背朝向 | 基线 8/8 同时回答正确 | 这组无遮挡、大幅度位置差异可被识别；不是复杂场景准确率 |
| 已给定朝向和镜像的纯文本换算 | 候选 A 在正面条件下 8/8 明确给出相反的自身方向 | 此处根本没有图片，问题至少包含参照系推理或指令遵循 |
| 补全通用换算关系的候选 B | 能答对个别文本条件，仍多次混淆画面与身体；正面图像 2/2 给错自身方向 | 不能把写清规则当作可靠性保证 |
| 正面人物靠右、要求走到画面中间 | A、B 各 2/2 说自身左侧，正确应为自身右侧 | 候选不采用；基线多用画面方向回答，也没有稳定满足身体参照要求 |
| 聚焦嘴部表情，切片上限 1 / 4 | 明确作出与人工标注一致的观察分别为 3/6、6/6 | 更细图像输入值得继续对照；样本太小，不能宣称已解决微笑识别 |
| 原生标签 | 92 次均有文字；0 次合法 speak，6 次合法 mode:guidance | 内容和协议必须分开评价；不能用文字回复证明原生说话标签合格 |

上一轮“反方向移动也获得认可”的现象还涉及当前目标是否被维持、是否比较了新旧画面，不能由本轮单张图片诊断确定唯一根因。上一轮双工只有 listen、没有回答的问题也仍未定位，见 [活力照片指导](2026-11-07-guidance-scene.md)。

## 单一提示问题：人体左右参照

生产基线没有明确的人体左右换算规则。A 先测试简短、通用的提醒；失败后，B 只把同一个问题的换算关系写清。两者分别和相同基线比较，不把 A、B 累加，也不增加固定姿势、构图或强制动作输出。

候选 A 相对正式提示词：

```diff
 不自行规定审美目标。用 speak 与用户沟通，结合后续画面继续观察和调整。
+给真人的左右建议以他自己的身体为参照，结合朝向和镜像关系把画面目标转成可执行的方向；关系不确定时先确认。
 用户邀请你一起拍照、合影或合照时，用 mode:co-photo 切换到合照互动。
```

候选 B 相对正式提示词（替换 A 的实验段落，不同时加入）：

```diff
 不自行规定审美目标。用 speak 与用户沟通，结合后续画面继续观察和调整。
+给真人的左右建议以他自己的身体为参照。人正对镜头且画面未镜像时，画面左右与他自身左右相反；背对镜头时相同；镜像时再反转这个对应关系。先结合朝向与镜像把画面目标换算成他该走的方向；侧身或对应关系不明确时先确认。
 用户邀请你一起拍照、合影或合照时，用 mode:co-photo 切换到合照互动。
```

例如，人正对镜头、未镜像且位于画面右边，走向画面中心应该往**他自身的右边**。背对镜头则应往自身左边；镜像会反转对应关系。侧身时，画面横向位移可能对应人的前后方向，不能总压缩成自身左或右。实际系统还需要知道镜像发生在输入图像还是仅预览显示，不应只靠“自拍摄像头”猜测。

## 结果解读

A 的正面纯文本 8 次均明确给出错误的身体方向。B 虽有正确答案，也有“背对镜头时左右相同”之后又要求反向移动的自相矛盾回答。它不是仅缺一条定义，当前组合也有应用规则不稳定的问题。仅凭本轮不能区分基础模型、推理模板、采样配置和较长系统提示各自贡献；仍需在固定部署上继续诊断，不能宣布这是整个模型家族的能力上限。

图像方向题中，A 的背面两次分别给出自身右（错）、自身左（对）；B 的背面两次均给出自身左（对），但两版正面两次均为自身左（错）。基线还出现把右侧说成“基本在中央”、把后视说成“面向画面右侧”的输出，与独立基础识图题全对并存。**会在一个问题中认出位置，不保证在指导任务中始终依据该位置推理。**

表情题的观察通过率：slice=1，中性 1/3、微笑 2/3；slice=4，中性 3/3、微笑 3/3。服务返回的 kv_cache_length 分别为 461–475 与 727–733，支持输入处理规模发生变化，但它包含生成部分，不是独立的切片计数，也不能据此精确还原切片数量。未检查服务内部张量；不能把请求上限 4 写成“每次实际正好 4 片”。该对照只发生在 chat，并不证明实时双工能使用同样设置或达到同样效果。

严格流式解析和整段解析均只识别出 6 个 mode:guidance，全部发生于已经处在 guidance 的诊断请求；没有执行切换，正常客户端收到同模式标签也不会重建会话。0 个合法 speak、0 个 blank。`说话：<speak>…` 或 `</speak>` 等不符合项目的 `<speak:内容>` 协议。普通文字适配未运行，不能虚报其成功数。标签问题留在原有记录，不在本轮同时改协议。

## 官方资料与工程判断

以下资料于 2026-11-07 查阅，工程建议不是已经集成或实测通过的组件。

[MiniCPM-o 4.5 官方论文](https://arxiv.org/html/2604.27393v1) 说明：双工流式视觉使用最高 448×448 分辨率，其他模式最高 2240×2240；每个图像切片的 1024 个编码 token 被压缩为 64 个。这支持“小脸、细手势可能受细节预算影响”的假设，但论文通用视觉基准不等于摄影到位验收。当前客户端发送 JPEG 且默认 max_slice_nums=1；本轮 PNG chat 诊断不能当成正常实时输入完全相同的复现。

[ViewSpatial-Bench 原论文](https://arxiv.org/abs/2505.21500) 发现相机视角定位和人物视角定位的表现存在差距。它支持把参照系转换作为独立能力评估；这里不声称该论文直接评测了本部署的 MiniCPM-o 4.5。

当前客户端是 Python / OpenCV 程序：已有麦克风及缓冲、CameraSource、CanvasSource、SpriteController、SpeechQueue、模式会话和流式标签分发。尚无人体、脸部或参照物检测器。SpeechQueue 当前打印文字，初始化 use_tts=False，接收端忽略音频输出，因此不能描述为已启用语音输出。相机代码未显式调用左右翻转；实际采集设备或显示链路是否镜像仍需确认。

| 需求 | 可评估的开源组件 | 能提供什么、不能替代什么 |
|---|---|---|
| 身体姿态 | [MediaPipe Pose Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker) | 33 个身体关键点，图像及 3D 相对坐标，适合第一步持续观测；不直接判断所有摄影姿势是否美观、是否达成语义目标 |
| 脸部可见动作 | [MediaPipe Face Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker) | 478 点、52 个表情 blendshape 系数，可辅助嘴角、眼睛、头部状态；52 个系数不是 52 种心理情绪 |
| 更细的全身 / 手部姿态 | [MMPose：RTMPose / RTMW](https://github.com/open-mmlab/mmpose) | 包含 133 点全身、手、脸等任务，作为需要更细观测时的备选；本项目尚未对它与 MediaPipe 做速度或精度比较 |
| 树、红色标志、栏杆等参照物 | [Grounding DINO](https://github.com/IDEA-Research/GroundingDINO) | 根据图片和文本短语返回目标框及匹配分数；需处理多个相似物体、漏检和文字指代歧义 |
| 连续跟踪已选对象 | [SAM 2](https://github.com/facebookresearch/sam2) | 提示式图像 / 视频分割和时序传播；不是独立的“识别一切对象名称”模型，可由检测框或用户点击初始化 |

大量动作类别的分类器不是必要起点。关节位置、身体朝向、嘴角变化等连续观测，更容易组合成新的摄影目标；“举手”“侧身”“扶物体”不必全部预先枚举进 prompt。若未来需要识别跳跃、跑步等完整动作，再评估时序动作模型。

建议保持以下分工，并用实际场景逐步验收：

1. **LLM 负责拍摄意图、场景理解和方案。** 根据可见可接近的环境提出自然互动，例如借栏杆形成斜线、手扶电话亭边缘、沿草地迈步；动作幅度随用户想要的风格调整，不默认越夸张越好。先提供可接受的建议，再根据用户反馈调整。
2. **视觉模块负责可观察证据。** 提供带时间戳、置信度的关键点、人物位置、参照物区域；低置信度输出未知，不替模型编造姿态。轻量检测可在客户端独立线程 / 进程运行，较重检测可在服务端，避免阻塞现有输入流。
3. **小型状态与几何模块负责当前目标和验证。** 保存用户此刻接受的目标、参照系、对象、容差。先确认镜像与朝向，再转换方向；用连续若干新帧判断达成，减少一帧抖动导致的“可以了”。用户改变主意就替换目标，旧移动要求立刻失效。LLM 仍负责自然表达，不增加 ON/OFF 动作权限。

“人在红色标志的画面右侧”：检测并持续跟踪人和标志后，用相对位置就能辅助检验；LLM 解释“哪一个标志、什么构图”。这通常不需要为每种站位单独训练一个模型，但也不能只信 LLM 的口头认可。

“树旁”：如果只指照片中靠近树，二维位置或区域距离足够形成构图判据；如果要求现实中靠到树边，还涉及深度，单幅图像中的相邻不等于真实距离近，需要额外深度、视角信息或用户确认。“手扶电话亭、身体靠栏杆”还涉及接触关系，手部关键点与物体区域接近只能作证据，二维重叠不能证明真的碰到或承重。

优先验证人体位置、朝向和左右校准，再加入脸部观察，最后增加参照物定位与跟踪；不建议一次装入全部模型。更好的环境互动建议也应单独做下一轮 prompt 实验，不与方向和感知模块集成同时修改。本轮未改生产 prompt，未安装或接入上述组件。
